# 统一延迟任务

在后台「延迟」添加监控，统一填写名称、目标、5–3600 秒间隔，并选择运行节点。新任务默认 60 秒、选中当前全部节点、开启新节点自动加入。「按节点」只选择已有监控，不再填写地址覆盖。

WSS 总开关、时段、自动发现、前端连接超时和历史点数位于「设置 → 采集和连接」。节点自身的系统采集间隔、上报间隔、WSS 上报间隔、接口与连接模式仍在节点的 Agent 设置中；这些控制系统指标和传输，不等于任务的探测间隔。原有 TCP/ICMP 节点设置及主机/IPv6/端口校验保持有效。

## 升级 Worker 后，再升级 Agent

支持 schema 9 的 [Agent v1.3.0](https://github.com/emailtq/cfsm-agent/releases/tag/v1.3.0) 已发布。已启用自动更新的节点按既有更新周期升级；其他节点可从后台安装入口指定 v1.3.0。本轮发布不会主动重装节点。

- 新 Go Agent 声明配置 schema **9**。Worker 下发该节点已关联任务的 `{id,target,interval}`；单个网络 worker 串行运行到期任务，报告只有指标 ID 与数值。未激活统一任务的站点下发 `latency_tasks=null`，继续原采集合同。
- 已发布的 v1.2.0/schema **8** Agent 保持可用：从当前任务生成固定槽与额外 ID 的兼容目标配置，节点关联和目标修改能生效，仍按原约 **20 秒**周期探测，不能执行每任务间隔。
- schema **3–6** 只支持原四槽，schema **7** 只支持原八槽；新增任务及额外数量需要升级。

数量没有业务上限；**每节点下发的目标配置**仍受原 64 KiB 字节边界约束，上报仍受既有字节与样本限制约束。不同节点的独有目标不会因全目录相加超过64 KiB而无法迁移。超过八项仅提醒 CPU、网络、采集和存储成本，不阻止添加。串行调度不会创建每目标 goroutine；大量超时目标可能延后下一轮实际探测。

## 迁移保留原配置与历史

首次打开统一任务页面，以当时有效配置创建独立 `settings.latency_tasks` 文档：

1. 按原槽分别读取全局目标、逐节点覆盖、空值继承和 `0` 禁用。
2. 同一槽的不同目标成为不同任务，各节点明确关联自己的有效目标。全局目标任务开启自动加入，独有覆盖任务不开启；禁用节点不被强行重新关联。
3. 原额外任务保留稳定 ID。迁移任务使用原 20 秒间隔，新建任务才默认 60 秒。
4. 文档保存原全局配置、各节点原槽值以及节点/槽/指标 ID 的迁移来源。原历史表、旧表及固定历史列不删除，不清库。

`settings.latency_tasks` 是CAS根记录；完整文档以 `latency_tasks:document:*` 有序分块保存，每块最多32768个UTF-16码元，边界不拆开emoji等字符的代理对；`latency_tasks:active:*` 和 `latency_tasks:seen:*` 保存D1写时过滤需要的有界片段。整次根切换、片段替换和显式历史删除在同一D1事务内完成；根使用唯一写入身份，失败的CAS不会覆盖赢家的片段。这样大节点关联、原配置和多代归档不集中在一个受D1 2MB限制的行内。未分块的旧文档仍可读取，下次实际修改时转换；没有新增表或人为任务数量门槛。

激活后，旧地址字段不再决定 Agent 配置；普通设置或节点编辑若继续提交旧地址字段，会返回 `latency_tasks_authoritative`。旧格式备份仍能导入，并转换成中央任务。中央任务备份保留任务和来源；不存在的节点不运行任务，其原关联留在 `imported_legacy.tasks` 中供恢复。

原固定槽历史以**节点与槽**为来源，在迁移时间之前投影到对应指标 ID；不同节点的不同目标不混合。旧格式没有记录每次历史目标变更，因此来源保存的是迁移时有效目标及原槽，不补造更早的地址版本。原列始终可回溯。

## 改目标使用新指标身份

- 改名保留任务 ID 和指标 ID。
- 改目标保留管理任务 ID，生成新的 `metric_id`；此前配置归档，旧目标数据不会成为新目标曲线。
- 删除后再添加使用新 ID。删除确认会删除该任务各代 ID 的 JSON 延迟历史，保留原始固定槽历史及可回溯配置。D1 在写入时按当前任务/关联过滤指标，延迟到达的旧报告不会复活已删除指标。
- 保存节点关联只应用相对打开时 `base` 的增删差量，保留期间自动加入的新节点和其他编辑者的独立改动。排序和文档写入使用 D1 CAS；冲突返回 409，而不是覆盖新状态。

目标地址和原配置只在已认证管理/Agent 配置通道出现。公共配置和实时数据只提供 ID、名称及数值，不带目标地址；节点详情和卡片按自身任务关联显示。

## 本地验证入口

`node --test test/latency-tasks.test.js` 使用现有 Miniflare/D1 与真实 Go 测试二进制，覆盖 9/32 任务配置、实际 TCP 探测、HTTP/WSS、历史和公开投影。缺少相邻Go Agent/既有Go工具时只跳过真实Go用例，其余Worker回归继续运行。

`node --test test/frontend-unlimited-ping.test.js` 使用现有 Vue/Playwright fixture，自己生成合成schema9报告，经真实认证Worker/D1/DO驱动浏览器，不依赖另一个测试先写Go报告。实际参考验收用 `node test/fixtures/admin-ui/latency-tasks.mjs --reference`，额外渲染相邻minimal真实React/Radix/Tailwind/Sonner实现。若需沿用已完成Go用例的真实报告，设置 `CFSM_LATENCY_GO_RECEIPTS` 指向其证据目录；这是显式重放，不与并发 `npm test` 共用待生成文件。

物理 Android 输入法需连接设备后复测；CDP 触摸与 visualViewport 验证不等同于系统 IME 实测。
